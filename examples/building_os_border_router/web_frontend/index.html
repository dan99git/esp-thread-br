Commissioning Model

Reachable hardware stays floating until the site package expects it, the operator identifies it, and the spatial identity is imprinted.

  1. 1Activate site packageImported `.recad` gives planned fittings and expected product identity.
  2. 2Discover floating hardwareThe BR can see hardware on the mesh, but that is not a pairing decision.
  3. 3Gate by model_idOnly exact expected matches become pairing-ready; surplus or missing identity stays held back.
  4. 4Identify in placeFlash/blink the fitting and confirm the physical position one by one.
  5. 5Imprint and deployWrite the spatial identity, register the device, then push the compiled ledger.

Identity Boundaries

Hardware identity, spatial identity, product identity, and transport address are separate values.

  • Hardware: unique device identifier used to find a physical unit.
  • Product: broadcast model_id used for strict expected-match checks.
  • Spatial: assigned only after pairing to a planned position.
  • Transport: current address/path, never identity evidence.

Working Decisions

Keep the operator workflow above the raw Thread controls.

  • Raw Thread join is not BOS commissioning: discovered Thread networks can be nearby Nest or other fabrics. Normal BOS commissioning must not press Join on random scan results.
  • Floating hardware is not registered hardware: reachable devices stay floating until the active site package expects them and the installer confirms the physical unit.
  • Spatial identity is assigned during pairing: hardware identity is used to find the unit; spatial identity is written only after binding to the planned position.
  • Hex transport IDs are not BOS identity: Thread addresses, RLOC values, PAN IDs, and XPAN IDs are diagnostics, not the persistent device identity.
  • Ethernet is the BR upstream path: the BR bridges site-server management to Thread devices. It is not the general Wi-Fi AP for high-bandwidth devices.
  • AI control must be surface-neutral: an agent should use skills, CLI, REST, and WebSocket/event data. The UI should describe the workflow but not become the only control path.
  • Ledger distribution target is BR as primary seed: the site server should push a verified ledger to the BR, then the BR advertises and serves it to mesh nodes.

BR Commissioning Workflow

The BR is infrastructure. It should be claimed to the site network, not paired as a room fitting.

  1. 1Boot on EthernetConfirm IP, upstream reachability, and BOS diagnostics on port 80.
  2. 2Find site serverUse configured URL or discovery, then register through the site-server API.
  3. 3Claim infrastructureBind the BR to site/building/level/network segment/cabinet metadata.
  4. 4Provision trustPersist token/API credentials and require them for future writes.
  5. 5Verify ThreadCheck dataset, channel, role, RCP, and on-mesh reachability.
  6. 6Expose floating queueReport visible hardware without turning visibility into pairing.
  7. 7Deploy ledgerReceive, validate, store, advertise, and seed the active ledger.
  8. 8Report convergencePublish seed/leech/stale/offline state back to the site server.

Known Gaps

Do not hide these behind UI copy.

  • Ledger ingress: /bos/ledger/push now stages to the inactive partition and swaps active metadata, but full zcbor decode, replay/downgrade checks, audit, and hardware verification are still pending.
  • Mesh serving: the BR seed resources /mesh/ledger/manifest, /mesh/ledger/chunk, and /mesh/have are present; XIAO source now pulls and activates the BR ledger over CoAP, pending hardware proof.
  • Convergence: SRP/TMFS DNS-SD browse now feeds peer rows; XIAO source publishes staging and active ledger TXT keys for lv, ld, have, and chunks, pending live peer-row verification.
  • Auth: BR claim stores a device token and sends it on status and convergence heartbeats; production still needs role/policy, audit, rotation, and transport hardening.
  • Offline handling: firmware now posts convergence snapshots to the site server; stale/offline timing still needs hardware proof with real peer rows.
  • BR identity: the site server stores BR placement in a dedicated infrastructure record; the compatibility device row is not a luminaire spatial identity.

Next Implementation Order

  1. Protect BR writes with device token/API key handling.
  2. Connect BR infrastructure placement to the site manager and agent policy surfaces.

  4. Add leaf TXT publication for lv, ld, have, and chunks.
  5. Verify SRP/TMFS peer rows and ledger progress on hardware.
  6. Prove stale/offline timing and convergence reporting on hardware.
  7. Add protected OpenAPI plus a border-router skill that calls CLI/REST.
  8. Flash and verify the unified port 80 UI and BOS diagnostics routes on hardware.
